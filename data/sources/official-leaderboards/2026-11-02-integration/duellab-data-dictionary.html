GameBench 2 — Public data

Data dictionary

Definitions for leaderboard JSON, CSV, Parquet, Charts, summary, and release-manifest fields. Contract versions are explicit so historical releases remain interpretable.

Files and versions

  • leaderboard.json (v12 schema): Index of the leaderboard/ part files, with row counts and SHA-256 checksums. Releases before v12 carry every row in this one file.
  • leaderboard/<leaderboard>.json and leaderboard/<leaderboard>/<game>.json (v12 schema): Canonical track rows for one leaderboard, and its per-game rows for one game. Concatenating the parts in index order gives the full ordered row list.
  • leaderboard.csv (v12 projection): Flat projection of the same ordered rows in one file. Numbers are rounded to six decimal places.
  • leaderboard.spreadsheet.csv (Spreadsheet view): The same rows for opening in a spreadsheet. Cells beginning with formula markers or tab/newline controls receive an apostrophe so they import as text, including negative numbers. Use JSON or Parquet for full precision, or the canonical CSV above (six decimal places).
  • leaderboard.parquet (v12 metadata): Arrow-typed identity, status, rank, eligibility, score, and lossless row JSON in one Snappy-compressed file.
  • publication_readiness.json (v3 block): Earned evidence states: preliminary (every draw at the 48-draw checkpoint is a complete two-seat pairing; no precision claim) and interval_validated (a 95% interval from a method validated across programs, not guaranteed for each program; it describes the target-weighted pairing score from 0 to 1, not the 0–100 score; precision_target_met says whether its half-width is within 0.05; published only for an interval method the release's state policy qualifies; a state carried forward from an earlier target with another method is published as preliminary when its interval came from the preliminary checkpoint, and not at all otherwise). When the state policy qualifies a method, interval_validation records its validation: the analysis and its SHA-256 (qualification_evidence), the date (validated_on), the evidence it ran on (validation_evidence_commit_sequence, validation_evidence_versions), and carry_over: the validation carries over across engine and SDK upgrades, so it applies to results pooled across versions. Every state carries the population_revision (SHA-256 of the target population), the evidence_commit_sequence, and the earned_report_sha256 and earned_state_policy_sha256 it was earned under; a row state also carries its target_revision (SHA-256 of the row's whole target, including its own program weights). counts.target_excluded_programs is the number of programs that cannot be scored reliably (quarantined by the benchmark worker; a crash or illegal move counts as the faulting program's loss instead) and so leave every target; target_exclusion_policy names the list's rule (readiness_target_exclusions_v2). current_state marks a state carried forward from an earlier target and gives its state under the current target. Programs are keyed by E- ID and appear only beside rated rows; model/setting rows by pooled model key, request_mode and effective_request_value, with per-game states keyed by public game alias. An absent key means no earned state: not yet earned, target undefined, an unrated row, or no single matching public row.
  • charts_data.json (v2 schema): Overall rank, status, reasons, match, game, cost, and chart series.
  • benchmark-summary.json (v4 schema): Release-bound population counts and ranked Reasoning Variants leaders.
  • release-manifest.json (v6 schema): Release identity, counts, hashes, citation, and immutable URLs.
  • route-inventory.json, in the prepared release pair (v1 schema): Canonical-to-physical mappings, aliases, hashes, and per-route release evidence.

Row identity and joins

canonical_public_row_identity is the public key for one row in one benchmark view of this release. Reasoning Variants identities bind the model to an evaluated-setting tuple; equal-looking setting labels (Baseline, Balanced, Intensive) are never a join key. Join JSON, CSV, and Parquet on this field. Join Charts to Overall rows with its same identity. Across releases, reference a result by public_release_id together with this key (see Importing results).

evaluated_setting_identity is evaluated_setting_identity.v1: canonical provider route and model, request mode and effective request value, prompt and prompt-profile identities, output mode, reasoning policy and catalog identity, plus resolution_status. exact means the complete tuple was retained; opaque_historical preserves older evidence without inventing missing request details.

Reasoning settings

On Reasoning Variants rows (track full_freedom/mixed, “Model + reasoning setting” on the site), the provider request is recorded in evaluated_setting_identity: request_mode and effective_request_value. Classify a row from those two fields, never from its label.

  • resolution_status describes the whole identity: route, model, request, prompt, output mode, policy and catalog. opaque_historical means at least one of them was not retained, often the prompt or output identity. It does not mean the effort is unknown.
  • reasoning_setting is the release's public setting key, such as historical-provider-setting-intensive, with -variant-N when a model has several requests in one group; variant numbers follow position within the release. reasoning_provenance.requested_reasoning_effort, provider_reasoning_params.requested_effort and the CSV column requested_reasoning_effort hold the same key. None of them is the literal request. In entrants.json, reasoning_setting is each program's recorded value.
  • On these rows, evidence_status and bracket_eligible in provider_reasoning_params follow resolution_status: while no row's identity is exact, they read retained_literal_legacy and false on every row and say nothing about whether the request is recorded. On the Baseline, Balanced and Intensive leaderboards they tell whether a group's setting is the model's documented one.
  • reasoning_level is the display label: the current capability catalog's wording for the recorded value, so its text can change between releases. reasoning_bracket is the group, and is null for a shared budget. Neither is a join key.
  • The Baseline, Balanced and Intensive leaderboards have one row per model and group. A row there can pool several requests of its group, so it is not one setting; use Reasoning Variants rows for single settings.

Request classes, by request_mode and effective_request_value:

  • literal_effort: effort with a level such as low or xhigh. A recorded effort level. 183 rows in this release, 168 ranked.
  • disabled: none under effort or toggle. Reasoning turned off. 53 rows in this release, 43 ranked.
  • enabled_without_levels: toggle with enabled. Reasoning turned on; the model has no levels to choose. 19 rows in this release, 14 ranked.
  • field_omitted: omitted with none. No reasoning field was sent. Not the same as disabled. 4 rows in this release, 3 ranked.
  • provider_default: omitted with default. The model offers no reasoning control; the provider default applied. 2 rows in this release, 2 ranked.
  • shared_budget: budget. One historical thinking budget that served more than one reasoning group; the row has no group. 1 row in this release, 1 ranked.
  • other_recorded_value: any other recorded value. A recorded request outside the classes above. 0 rows in this release, 0 ranked.
  • unresolved: an effective_request_value of historical-… or unknown_legacy. No row-level request value. Unknown is not zero, disabled, low or the provider default. 0 rows in this release, 0 ranked.

Importing results

  1. Pin one release. Use public_release_id from release-manifest.json and cite the immutable releases/<public_release_id>/ copy. Check leaderboard.json against the manifest's artifact_sha256, and each part's size and SHA-256 against the index. On rows, results_cut_id equals public_release_id; snapshot_id and comparability_tuples[].results_cut_id carry an internal build identifier; cite the release ID instead.
  2. Choose the view. overall has one row per model. A row with an official rank scores the mean of the model's three group scores; a model with results for fewer groups is listed without a rank, and its score averages only the groups it has. full_freedom/mixed (Reasoning Variants) has one row per evaluated request; use it for single settings. The Baseline, Balanced and Intensive leaderboards have one row per model and group, which can pool several requests.
  3. Select eligible rows. For fully eligible results, keep ranking_status ranked with eligibility_flag true. A rank alone is not enough: partial Overall rows carry official ranks with incomplete evidence. After this filter the source ranks have gaps; keep them, or label positions you number yourself as yours. Provisional rows have no rank, and their scores rest on incomplete evidence; never sort them among ranked rows.
  4. Keep Overall, single settings and best settings apart. A ranked Overall score is DuelLab's mean over a model's three groups. A “best setting” is your own statistic over Reasoning Variants rows: say which rows it chose from and how it breaks ties, keep the chosen row's key, and do not call it Overall.
  5. Map settings by class. Use the classes under Reasoning settings. Do not map an unresolved value to a standard effort name, and do not treat unknown as zero, disabled, low or the provider default.
  6. Keep the source identity. model_slug identifies the model in a release; dated versions have their own slugs (a -0902 suffix, for example) and separate rows and scores. model_display_name is for display and need not be unique. On Reasoning Variants rows, evaluated_setting_identity.provider_model is the provider's model identifier. Store these beside your own catalog ID.
  7. Reference a result by release and key. canonical_public_row_identity identifies a row within one release. Reference an imported result as public_release_id plus that key. A key can change between releases without any change in the result: Overall keys include the reasoning catalog's digest, and variant numbers are positional. Establish any cross-release match explicitly.
  8. Keep the precision. JSON and Parquet carry full double precision; the CSV is rounded to six decimal places. Consecutive releases can differ by less than a displayed digit, so a rounded value does not identify its release on its own. Compare at half a displayed unit.
  9. Attribute. The data is published under the manifest's data_license (data_license_url), with its citation (citation_url). Link the immutable release and state your selection rule.

Ranking, eligibility, and nulls

ranking_status is ranked, provisional, partial, or not_applicable. Overall rows with ranked or partial status share one score-ordered official rank sequence. A partial row keeps eligibility_flag=false and its reason codes because its evidence is incomplete. Reasoning Variants rows with provisional status remain unranked. A null rank/official_rank means no official rank, not zero or tied-last.

Reason codes are missing_bracket_scores, unknown_capability_evidence, missing_or_non_distinct_settings, untested_or_ineligible_settings, missing_generation_quality, generation_incomplete, below_generation_quality_threshold, fixed_coverage_incomplete, and grouped_stability_incomplete. Current official-qualification rows distinguish an unfinished generation cohort, an actual generation-quality failure after completion, incomplete fixed opponent-and-seat coverage, and grouped rating evidence that is not yet stable. Historical rows without an official-qualification marker retain the generation-only compatibility reason. A Partial 3/3 row has all three score values but fails at least one other eligibility condition named by these codes.

Other null numeric fields mean the measurement is unavailable or not applicable. They never mean zero. Empty arrays mean no observations of that kind were retained.

Measures and units

  • score and min/max displays use the documented public 0–100 scale. No uncertainty is published or displayed (uncertainty is null).
  • headline_games on a track row (JSON and Parquet row JSON; headline_games_json in CSV) gives each game's headline value, keyed by public game alias: score (the working programs' scores weighted by the attempts that produced them, plus 0 for each model-caused failed generation attempt, divided by those attempts), playable (the working programs' attempt-weighted mean), attempts and failed_attempts. A row's score is the mean of its games' score. Overall is the exception: its score is the mean of the setting scores, and its game values are each game's mean over the settings, so they need not average to it. Game rows (row_kind game) and the Charts series per_game_tracks and per_game_all are working-program strength: they leave failed attempts out, so they do not reproduce the headline. Charts carries the headline values as headline_games_tracks and headline_games_all; its per-game charts read their score (headline score) or playable (working-program strength). Since 24 October 2026 a setting's game rows and per_game_tracks equal its playable values (they pool every working program of the row, weighted by attempts); per_game_all is the mean over the three settings and has a value only where all three do. Charts model rows also carry diagnostics: working_program_strength (a setting's value equals that leaderboard row's conditional_success_score; all is the mean of the settings), program_outcomes (generation outcomes and success_rate, the row's plugin_success_rate), official_rank_by_reasoning and economics_best_value.
  • Game rows with several programs (from 25 October 2026): a game row (row_kind game) stands for all of a model's programs in that game and setting. score is their working-program strength, weighted by attempts; raw_elo is the attempt-weighted mean of the working programs' raw ratings, weighted like working-program strength (a failed attempt has no program and no rating); wins, losses, draws and rated_matches are the programs' combined record, which measures evidence volume, not strength; contributing_entrants counts the programs, and a track row's entry_count (the Players column) counts the programs of its game rows (Overall: of its settings). Added fields: working_attempts and counted_attempts (“N working of M attempts”: counted attempts are the working ones plus those that failed in model-written code; too-slow programs and provider, API or test-machine faults are not counted) and program_raw_elo_low and program_raw_elo_high (the lowest and highest program rating, only for rows with two or more rated programs; a description of the programs, not a confidence interval). CSV carries the four after headline_games_json; they are absent on track rows and earlier releases. On the Intensive, Balanced and Baseline leaderboards a model row's wins, draws and losses are the sum of its game rows' records (Reasoning Variants rows already were), and Charts' per-game match totals equal the game rows'. Charts model rows carry game_gaps: per view and game without a working-program strength, why it has none: failed (every counted attempt failed, a recorded 0 in the headline), too_slow (rejected by the speed check, not counted), infra_excluded (lost to a provider, API or test-machine fault, not counted), unrated (a working program not rated yet) or untested (no attempt recorded).
  • conditional_success_score on a track row keeps its field name for compatibility. It is working-program strength, the leaderboard's column of that name (called Playable before 24 October 2026): the mean score of the working programs across games, with failed generation attempts left out. plugin_success_rate is the program success rate (working programs over counted attempts).
  • raw_elo and raw_elo_rating keep their names for compatibility. In this release they hold the B1 rating (a Bradley–Terry fit, points around 1500 with the game's programs centred) described on the Methodology page. They compare player programs within the same game, not with releases rated otherwise. No rating uncertainty is published.
  • Match counts are integer participant results; for model-setting rows, rated_matches = wins + losses + draws.
  • Opponents played (an optional leaderboard column, hidden by default) is Σ played ÷ Σ owed over the row's player programs, shown as a whole percentage rounded down. For each program in the Reasoning Variants data of entrants.json, owed_seat_pairings = 2 × (programs in the game − 1): the full matrix owes one rated match against every other program of the game, once with each moving first. played_seat_pairings counts those with at least one completed rated match. Overall rows pool the model's programs from the Baseline, Balanced and Intensive views; other rows pool the programs of their own view. Releases whose data was produced before October 8, 2026 lack both fields; they instead owe each other program once (programs in the game − 1) and count distinct_rated_opponents as played.
  • Rates are fractions from 0 to 1 in data, even when the site displays percentages.
  • Token counts are tokens; latency is milliseconds; generation time is seconds; USD fields are US dollars.

Cost evidence

Cost is an equal-weight mean across unique model/game/evaluated-setting cells. evidence_basis, cost_basis_counts, and pricing_table_versions disclose whether values are billed, provider-reported, versioned standard-list estimates, legacy, or combined. Exact zero is 0; a positive sub-cent value remains positive and must not be rounded to a displayed zero.

Example: a row with mean 0.0042, evidence basis “Standard list-price estimate,” and pricing revision pricing-v3 means an estimated 0.42 cents per unique cell under that revision—not a provider invoice.

Population counts

model_family_count counts unique model families. Model-setting counts separate total, ranked, and provisional reasoning settings. ranked_overall_model_count keeps its compatibility meaning of complete-evidence Overall rows; the total number of official Overall ranks is ranked_overall_model_count + partial_overall_model_count. unique_code_entrant_count deduplicates public code identities across the suite; per_game_unique_entrant_counts gives the corresponding count for each public game alias. model_count and reasoning_variant_count are temporary compatibility aliases.

GameBench 2 evaluates model-generated game-playing programs after compilation and execution on an evolving set of public benchmark games. Compiled programs play head-to-head, and the public methodology explains how those results become current standings.
